# สำรวจ Abdul ด้วย REA เพื่อปรับใช้กับบอทเรา

ตรวจวันที่ 8 พฤศจิกายน 2026 (เวลาไทย) — ผลสำรวจและข้อเสนอ ยังไม่ได้เพิ่มฟีเจอร์ให้บอท

## สิ่งที่ควรหยิบมาใช้ก่อน

**ทำให้สิ่งที่บอทจำไว้ ค้นเจอ ตรวจแก้ได้ และตามงานได้เหมาะกับความสำคัญของงาน**
บอทเรามีการจดงาน เตือนซ้ำ สรุปเช้า สรุปเย็น และแฟ้มลูกค้าแล้ว จึงควรต่อจากฐานนี้
สิ่งที่น่านำมาปรับใช้จาก Abdul คือค้นจากความหมาย คลังข้อมูลที่เปิดดูได้ การเตือนล่วงหน้า และระดับการทวงงาน

## ตรวจถึงไหน และเชื่อผลได้แค่ไหน

- REA เปิดหน้าแรก นโยบายความเป็นส่วนตัว ข้อกำหนด และหน้าแอปใน Chrome แบบโปรไฟล์ชั่วคราว แล้วเก็บ DOM/accessibility และเครือข่ายตามที่ระบุ
- หน้าแอปเปลี่ยนจาก `/` เป็น `/home` แล้วพาไป LINE Login จึงยังไม่ได้ทดสอบการบันทึก ค้นหา เตือน ลบ หรือเชื่อม Calendar ด้วยบัญชีจริง
- เก็บไฟล์ JavaScript ของแอปได้ 45 ไฟล์ รวม 987,986 ไบต์ เลือก 9 ไฟล์ที่เกี่ยวกับฟีเจอร์ให้ REA วิเคราะห์แบบ static: อ่านได้ 225,261 ไบต์ ไม่มี parse failure
- โค้ดฝั่งหน้าเว็บแสดงเส้นทาง หน้าจอ และฟิลด์ที่รองรับ แต่ไม่พิสูจน์ว่าหลังบ้านทำงานสำเร็จหรือเปิดให้ใช้ทุกบัญชี
- บาง response body เก็บไม่ได้เพราะเพดาน 64 KiB/ไฟล์ และข้อจำกัดจำนวนคำขอพร้อมกัน/จำนวน events ของ REA จึงไม่ได้ครอบคลุมโค้ดทั้งหมด ไม่มี source map หรือ source backend
- การดาวน์โหลดตรงจาก shell ได้ HTTP 403; ใช้เฉพาะ bytes ที่เบราว์เซอร์โหลดตามปกติและ REA เก็บไว้ได้ ไม่เรียก server actions หรือ API ที่พบเพื่อทดลองเปลี่ยนข้อมูล
- เทียบกับ source ของบอทเรา โดยไม่อ่านแชทจริง กุญแจล็อกอิน หรือ API key และไม่ส่ง WhatsApp/เรียก AI จริง

ใช้ป้ายหลักฐานสามแบบ: **ประกาศ** = เว็บไซต์/นโยบายระบุ, **พบโค้ด** = เห็นในไฟล์ที่ส่งให้เบราว์เซอร์, **ยังไม่ทดสอบ** = ยังไม่ยืนยันผลหลังล็อกอิน

## จุดที่ข้อมูลขัดกัน

1. ข้อมูล structured data หน้าแรกพูดถึงการรับเสียง แต่ **นโยบายล่าสุดระบุว่าเสียง/วิดีโอยังไม่อยู่ในกระบวนการรับข้อมูลปกติ** จึงไม่จัดว่ารองรับถอดเสียงแล้ว [E1, E2]
2. หน้าแรกพูดถึงสรุปเช้าของทีม แต่บางแพ็กเกจติดป้ายสรุปประจำวันว่าเร็ว ๆ นี้ จึงยังสรุปไม่ได้ว่าเปิดใช้แบบใดกับแพ็กเกจไหน [E1]
3. มี `googleDrive`, `dailyRecap`, `specialPersonality` ในชุด flags แต่การมีชื่อในโค้ดไม่ได้พิสูจน์สถานะเปิดใช้จริง [E7]
4. นโยบายพูดถึงโอกาสกู้คืนไฟล์ แต่ถังขยะในโค้ดส่วนที่เห็นบอกดูได้อย่างเดียว จึงยังยืนยันขั้นตอนกู้คืนของผู้ใช้ไม่ได้ [E2, E7]

## แนวทางระบบที่เรียนรู้ได้

สิ่งต่อไปนี้เป็น **ข้อสรุปจากนโยบายที่ผู้ให้บริการประกาศ** ไม่ใช่การตรวจระบบ backend:

- แยกงานให้โมเดลต่างชนิด: สนทนา/บันทึก/ค้นคืน, อ่านรูป/เอกสาร/สร้างภาพ, และจำแนกข้อความกลุ่มว่าเรียกบอทหรือไม่
- ใช้ embeddings กับเนื้อหาที่บันทึก และมีระบบค้นเว็บที่ดูแลเองพร้อม Firecrawl เป็นช่องทางสำรอง
- นโยบายระบุแยกข้อมูล Calendar ออกจากดัชนีค้นหา/embeddings โดยส่งบริบทที่จำเป็นให้โมเดลเป็นครั้ง ๆ
- ระบุฐานข้อมูล/คิว/ระบบหลักบน Railway และไฟล์บน Backblaze B2 ผ่าน Cloudflare [E2]

สำหรับบอทเรา หลักที่ควรรับมาคือแยก “รับข้อมูล → เก็บข้อมูล → ค้นหลักฐาน → เสนอ action → โค้ดลงมือทำ”
ใช้ `src/ai.js` เป็นทางผ่าน AI เดิม รองรับทั้ง Claude/OpenAI และรักษากติกาที่โค้ดเป็นผู้ยืนยันสิ่งที่ทำสำเร็จ
ไม่จำเป็นต้องเปลี่ยนผู้ให้บริการทั้งหมดตามเขา

## ลำดับที่เสนอสำหรับบอทเรา

นี่เป็นข้อเสนอสำหรับเลือกงานรอบถัดไป ยังไม่ได้อนุมัติหรือเริ่มพัฒนา

### 1. ความจำที่ย้อนดูและแก้ได้

เพิ่มหลักฐานต้นทางให้โน้ต: message IDs, ผู้ส่ง, เวลา และความสัมพันธ์ว่าโน้ตใหม่แทนข้อไหน
แล้วเพิ่มคำสั่งดูตามประเภท/ค้นในแฟ้ม/ปักหมุดรายการสำคัญ โดยยังใช้แชทเป็นทางเข้าหลัก

ตัวอย่างสมมติ: “บอท บ้านตัวอย่าง สเปกห้องน้ำที่ตกลงล่าสุดคืออะไร” → แสดงสเปกปัจจุบัน พร้อมบอกว่ามาจากข้อความไหน และมีข้อใดถูกเปลี่ยนแล้ว

จุดแก้: `src/db.js` (`client_notes`, `addClientNote`), `src/tasks.js` (`syncTasks`, `contextBlock`, `handleRequest`), `src/bot.js` (คำสั่ง)

เงื่อนไขผ่าน: หยิบหลักฐานผิดกลุ่มไม่ได้; แก้สเปกแล้วไม่ตอบข้อเก่าว่าเป็นปัจจุบัน; หาหลักฐานไม่ได้ต้องบอกตรง ๆ

### 2. ค้นจากความหมายร่วมกับคำตรง

แบ่งแชท/โน้ต/เอกสารเป็นส่วนที่มีแหล่งอ้างอิง แล้วใช้ทั้งคำตรงและ embeddings ช่วยค้น
ชื่อบ้าน รหัสวัสดุ และตัวเลขยังต้องค้นตรงได้ ไม่พึ่งความคล้ายของความหมายอย่างเดียว

ตัวอย่างสมมติ: ถาม “บ้านตัวอย่างที่คุยเรื่องน้ำรั่ว” ควรหาเรื่อง “ซึมตรงวงกบหลังฝนตก” พบได้ แม้ไม่มีคำว่าน้ำรั่ว

จุดแก้: `src/tasks.js` (Q&A/retrieval), `src/db.js` (ดัชนีและสิทธิ์ตามกลุ่ม), `src/ai.js` (ช่องทาง embeddings ถ้าเลือกใช้)
ต้องเลือกโมเดล/วิธีเก็บ embeddings และประเมินด้วยข้อมูลสมมติก่อน ไม่เพิ่มผู้ให้บริการโดยอัตโนมัติ

เงื่อนไขผ่าน: ค้นคำพ้องดีขึ้น; ชื่อ/ตัวเลขไม่เพี้ยน; ลบข้อมูลกลุ่มแล้วลบดัชนีด้วย; ผลค้นแต่ละชิ้นอ้างกลับต้นทางได้

### 3. เตือนล่วงหน้าและทวงตามความสำคัญ

แยก `due_at` ของงานออกจากเวลาส่งเตือนล่วงหน้า แล้วเพิ่ม policy การทวงรายงาน โดยเก็บเพดาน/ช่วงเงียบไว้
ตัวอย่างสมมติ: “บอท พรุ่งนี้ 10 โมงตรวจหน้างาน เตือนก่อน 30 นาที เรื่องนี้สำคัญ” → ยืนยันทั้งเวลานัดและเวลาเตือน

จุดแก้: `src/tasks.js` (`handleRequest`, `fireDueReminders`), `src/db.js` (reminders), และ config/docs ถ้ามีค่าที่ผู้ใช้ตั้งได้

เงื่อนไขผ่าน: เตือนล่วงหน้าไม่เปลี่ยนกำหนดส่ง; ไม่ส่งซ้ำจากการรีสตาร์ต; เลื่อน/ยกเลิกแล้วแก้ตารางเตือนครบ; เคารพช่วงเงียบ

### 4. Google Calendar เมื่อจำเป็นต้องแชร์ปฏิทิน

เริ่มจากแสดงตัวอย่างกิจกรรม วัน เวลา ระยะเวลา ปฏิทิน และผู้ร่วม ก่อนสั่งสร้างจริง
เก็บ external event ID เพื่อแก้/ยกเลิกและกันการสร้างซ้ำ แยก OAuth ของเจ้าของปฏิทินออกจากสมาชิกกลุ่ม
ปฏิทินส่วนตัวไม่ควรเผยในกลุ่มโดยอัตโนมัติ

### งานที่น่าสนใจเพิ่มเติม แต่ไม่ใช่ฟีเจอร์ที่ยืนยันจาก Abdul

เสียงหน้างาน → ถอดข้อความ → เสนอจดโน้ต/งาน และรายงาน VO/Defect เป็น PDF/ตาราง เหมาะกับบริบททีมเรา
แต่ไม่ควรอ้างว่าเป็นความสามารถที่ตรวจพบว่า Abdul ทำแล้ว งานเหล่านี้ต้องออกแบบและเลือกแยกต่างหาก
